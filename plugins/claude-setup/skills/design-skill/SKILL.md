# design-skill

**スキルを書く前の判断**を担う。公式の `skill-creator` が「スキルを書く」ツールなのに対し、
本スキルは「**そもそも書くべきか・境界はどこか・どう発動させるか**」を決める。

設計が固まったら `skill-creator` に渡す。無ければ §5 のリファレンスを見て直接書く。

- **Input**: `$ARGUMENTS` = スキル化したい作業の説明（無ければ聞く）
- **Output**: 設計判断の結果。「作らない」も正当な結論

---

## Phase 1. そもそもスキルが正解か

**ここが本スキルの中心。** スキルは万能ではなく、他の手段のほうが強い場面が多い。

### 判定表

| 状況 | 正解 | 理由 |
|---|---|---|
| 機械的に判定できる（フォーマット・lint・文字数・禁止語） | **hook** | 確定的に解ける問題を LLM に任せない（→V-1）。忘れようがない |
| 禁止したいだけ | **permissions の deny** | 呼ばせない（→S-1.3） |
| 1〜2行の前提や規約を、全作業で守らせたい | **CLAUDE.md に1行** | スキルにすると description が常時コンテキストを食う |
| **特定のファイル種別・ディレクトリでだけ効く規約** | **`.claude/rules/`（`paths:` 付き）** | 該当ファイルを読んだときだけ載る。CLAUDE.md に書くと無関係な作業中も載り続ける |
| **特定の操作の瞬間だけ思い出させたい**（例: `grep` を打つ直前に「`rg` を使う」） | **PreToolUse hook で docs へのポインタ1行を注入** | docs が効くかは「どこに書いたか」ではなく「**いつ届いたか**」で決まる。中身ではなく置き場所の1行だけ注入し、読むかは Claude に任せる。hook は fail-open（壊れても exit 0）にして作業を止めない |
| 手順が複数ステップあり、判断を伴い、繰り返される | **スキル** | ここで初めてスキルが効く |
| 独立したコンテキストで長く作業させたい | **agent**（`~/.claude/agents/`） | 主コンテキストを汚さない |
| 一度きりの作業 | **何も作らない** | その場でやる |

**スキルと rules の境界がよく迷う。** 分け方はこう:

- **rules** = 「そのファイルを触るなら常にこう」という**規約**。手順ではない
- **スキル** = 「この作業をやるならこの順で」という**手順**。呼ばれて初めて動く

「Python は型注釈を必ず付ける」は rules。「リリース手順を実行する」はスキル。

### 3回ルール

**同じ手順を実際に3回繰り返してから作る。**

先回りして作ったスキルは、たいてい実態とズレる。しかも使われないまま
description が全セッションのコンテキストを食い続ける（→C-1 帯域はゼロサム）。

「これから繰り返しそう」は根拠にならない。**繰り返した記録があるか**を確認する。
無ければ「まだ作らない」を提案し、3回目が来たら戻ってくるよう伝える。

## Phase 2. 境界 — 既存と被らないか

### 既存スキルを列挙する

```bash
ls ~/.claude/skills 2>/dev/null
ls .claude/skills 2>/dev/null
# プラグイン提供分は /plugin か settings.json の enabledPlugins で確認
```

### 被りを検査する

**description が近いスキルが2つあると、どちらも選ばれなくなる**か、間違ったほうが選ばれる。
これはスキルを増やしたときの最大の失敗モード。

チェック:
1. 新スキルの発動トリガーが、既存のどれかと重なっていないか
2. 重なるなら、**どちらかに寄せる**か、**トリガー語を明確に分ける**
3. 既存を拡張して済むなら、新規に作らず既存を直す

分けるときは「いつ使うか」を description に書き分ける。

```
✗ run-loop     「品質を改善するループ」
✗ quality-loop 「品質を上げるループ」        ← 選べない

✓ run-eval-loop   「スコアが閾値に達するまで自動改善。判定は LLM」
✓ run-bestofn     「N 案を並べて人が選ぶ。好みや曖昧仕様が効く分岐で使う」
```

## Phase 3. 発動条件を設計する

`description` は**カタログの一行**。ここだけを見て選ばれるので、
「何をするか」と「いつ発動するか」の両方を書く。

```yaml
description: {いつ使うか}。「{トリガー語1}」「{トリガー語2}」で発動。{使わない場面があれば明記}
```

- **「いつ呼ぶか」だけを書く。何をどうやるか（手順・段数・出力形式）は本文へ。**
  description に手順を書くと、Claude は本文を読まずに description の短縮版だけで動く
- トリガー語は**ユーザーが実際に打ちそうな日本語**を2〜3個。核心を先頭に置く。
  それ以上並べると重複か手順の混入に化けるうえ、`description` + `when_to_use` の合算は
  **1,536 字で切られる**
- 似たスキルがあるなら「〜の場合はこちらではなく X を使う」まで書く
- 長くしすぎない。全スキルの description が常時ロードされる（→C-1）

## Phase 4. 配置スコープを決める

| 置き場所 | 反映 | 適する場面 |
|---|---|---|
| `.claude/skills/`（プロジェクト） | **即時**（再起動不要） | そのプロジェクト専用の手続き |
| `~/.claude/skills/`（ユーザー） | **即時**（再起動不要） | 全プロジェクトで使う汎用手続き |
| プラグイン | **要再起動** | 他人に配布する |

### 注意

- **プロジェクトローカルはグローバルを上書きする。** 同名スキルがあると、
  プロジェクト側が優先される。配布物を展開したあと古い版が黙って使われる事故が起きる
- **プラグインは `claude plugin install` が成功しても、再起動するまで呼べない。**
  `claude plugin list` に enabled と出ていても `Unknown skill` になる。
  「install 成功」「enabled 表示」は使えることの証拠にならない
- **`~/.claude/agents/` はセッション開始時のみ読み込まれる。** agent を足したら再起動する。
  未登録のまま指定すると、警告なく general-purpose にフォールバックする

## Phase 5. SKILL.md の書き方リファレンス

`skill-creator` があるなら、ここまでの設計を渡して書かせる。無ければ以下に従う。

### frontmatter

```yaml
---
name: {kebab-case。ディレクトリ名と一致させる}
description: {Phase 3 で設計したもの}
---
```

サブエージェントで実行させる場合のみ追加する:

```yaml
context: fork
agent: general-purpose      # ← subagent: ではない。subagent: は無効で、黙って読み込まれない
background: false           # ← 途中でユーザーに問いかけるなら必須
model: opus                 # 任意
```

- **`agent:` を使う。`subagent:` と書くとスキルが静かに読み込まれない**
- **`context: fork` は既定でバックグラウンド実行**（Claude Code 2.1.218 以降）。
  対話を含むスキルは `background: false` を明示する。忘れると
  "running in the background" と返って往復が成立しない

### 実在するキー一覧（2026-08 / v2.1.220・公式ドキュメント照合済み）

**キー名を間違えると、エラーにならず静かに無視される。** 出典が古い記事や他ツールの
規約から写すときは特に注意する。

| キー | 用途 | 備考 |
|---|---|---|
| `name` | スキル名 | ディレクトリ名と一致させる |
| `description` | カタログの一行 | 発動判定に使われる。最重要 |
| `when_to_use` | 発動条件の補足 | description に連結され、**合算 1,536 字で切られる** |
| `allowed-tools` | **そのターンだけ承認なしで使えるツール** | 制限ではない（下記） |
| `disallowed-tools` | スキル有効中、ツールをプールから除去 | こちらが「制限」。次のメッセージで解除 |
| `user-invocable` | `false` で `/` メニューから隠す | Claude や親 Skill からは呼べる |
| `disable-model-invocation` | `true` で Claude の自動発動を止める | **subagent への `skills:` プリロードも塞がる** |
| `arguments` / `argument-hint` | 位置引数（`$name` 置換）/ 補完ヒント | |
| `context` / `agent` / `background` / `model` / `effort` | サブエージェント実行 | 上記参照 |

**⚠️ `allowed-tools` は「制限」ではない。** 公式ドキュメントの明記:
「It does not restrict which tools are available — 全ツールは呼び出し可能なまま、
未列挙のツールは通常の permission settings に従う」。しかも許可は**呼び出したターン限り**で、
次のメッセージを送ると消える。
**本当にツールを使わせたくないなら `disallowed-tools` か、permissions の deny を使う。**
`allowed-tools: Read Grep` と書いた評価器が Edit できないと思い込むのが典型的な事故。

**呼び出し制御の組み合わせ:**

| 設定 | 塞がる経路 | 残る経路 |
|---|---|---|
| `disable-model-invocation: true` | Claude の自動発動・`Skill()` 経由・プリロード | `/name` 直叩き、Read で本文を読む |
| `user-invocable: false` | ユーザーの `/name` | Claude / 親 Skill からの `Skill()` |
| **両方** | **すべて** → **誰も呼べない Skill** になる | Read のみ |

親から `Skill()` で呼ばれる内部スキルに `disable-model-invocation: true` を付けない。
プリロードしたい参照スキルにも付けない。

**よく見かける誤り:**

| ✗ 見かけるが存在しない／誤り | ✓ 正しい |
|---|---|
| `allowed_tools`（アンダースコア） | **`allowed-tools`**（ただし意味は上記のとおり承認であって制限ではない） |
| `invocation` | **`user-invocable`** |

### 本文

- **最重要ルールは冒頭に置く。** compaction 後に再付与されるのは各スキルの
  **先頭 5,000 トークン**だけ（複数スキルの合計 25,000 トークン・新しい順）。
  末尾に置いた禁則は、compaction を一度挟んだ瞬間に視界から消える
- **500 行以下に保つ**（公式の推奨）。長い参照資料は別ファイルに出し、
  必要になった時点で読ませる（→K-2.1）
- **手順を Phase に切る。** 各 Phase の入口と出口を明示する
- **理由を書く。** ルールの列挙より理由のほうが未知のケースに汎化する（→E-2）。
  `ALWAYS` / `NEVER` を書きそうになったら黄信号 — 理由を添えて書き直す。
  例外は「評価器は評価基準を編集しない」のような、自明で譲れない安全条件だけ
- **Gotchas を最後に置く。** 実際に踏んだ落とし穴だけ。想像で書かない。
  1件 = 見出し1行 + why と回避を1〜2行。前提が崩れたら削る（stale な Gotcha は無いより悪い）。
  **同じ失敗が再発するなら Gotchas 止まりにせず、lint / hook へ昇格させる**（→V-1.1）

### `!` 構文を使うとき

スキル本文の `` !`command` `` は**読み込み時に無条件でシェルを実行する**。

- 他人のスキルを導入する前に、`!` の中身を目視で確認する
- `!` の中身も権限チェックを受ける。**`find -exec` のような runtime-determined な
  コマンドが1つでも混ざっていると、headless ではスキルの発動そのものが
  静かに中断される**（0ターン・エラーなし・denial の記録もなし — v2.1.220 実測）。
  拒否されるのではなく「何も起きなかったことになる」ので、気づきようがない。
  `find -print` と `while read` の組み合わせに統一する
- `bypassPermissions` のセッションでは通ってしまうので、**検証が素通りする**。
  通常権限で確かめる

## Phase 6. 検証

作ったら**発動するかを確かめる**。書いただけでは分からない。

1. 新しいセッションを開く（プラグインなら再起動）
2. 設計したトリガー語で呼びかける
3. 意図したスキルが選ばれるか確認する
4. 似たスキルが誤って選ばれたら、Phase 2 に戻って description を分け直す

---

## Gotchas

- **「作らない」を結論にしてよい。** むしろ既定はそちら。
  スキルは増えるほど選択を難しくする
- **先回りして作らない。** 3回繰り返した記録を確認する
- **description の被りが最大の失敗モード。** 増やす前に必ず既存を列挙する
- **プロジェクトローカルがグローバルを上書きする。** 同名に注意
- **プラグインは再起動が要る。agents も再起動が要る。
  プロジェクト/ユーザースコープの skill は要らない。** ここを混同しない
