# モデル振り分け — 役割ごとに最適なモデルを割り当てる

Phase 3 で CLAUDE.md に「モデル運用」の節を生成するとき、および
カスタム agent・スキルを作るときに読む。

> モデル名・世代は変わり続ける（この文書の判断軸は世代に依存しないが、
> 例示のモデル名は生成時点の現行に置き換えること）。

---

## 1. 判断軸 — 「役割 × 検証可能性 × 量」

モデルの強弱を割り当てる基準は3つだけ。

| 軸 | 強いモデルへ | 軽いモデルへ |
|---|---|---|
| **役割** | 司令塔・計画・統合判断・レビュー（判断が濃い） | 手を動かす作業（判断が薄い） |
| **検証可能性** | 出力を機械で検証**できない**もの（設計・評価・文章の質） | テスト・型・lint で**機械検証できる**実装 |
| **量** | 1回の重い判断 | 並列・大量・繰り返し |

原理: **検証器があるなら、生成側は軽くてよい**（間違えても機械が止める）。
検証器が無い判断こそ、強いモデルに払う価値がある。
逆に「運転役（オーケストレータ）」は状態管理と例外処理を取りこぼせないため、
**常に最強を固定**する — 安い被験役を何体でも安全に回せるのは、運転が固いから。

もう1つの原理: **モデル能力とハーネスの厚さは反比例する**。
軽いモデルを使う場所ほど、ハーネス（チェックリスト強制・ステップ検証 hook）を厚くする。

## 2. 典型の割り当て（雛形）

生成する CLAUDE.md の節はこの形（**グローバル CLAUDE.md に既に方針があるなら、
プロジェクト側は差分だけ書く**。同じ内容の重複は帯域の無駄）:

```markdown
## モデル運用（グローバル方針との差分のみ）
- 司令塔・計画・統合判断: 最上位モデル
- 実装サブエージェント: 中位モデル（テスト・型が検証器として立っている前提）
- レビュー・評価: 上位モデル（検証器が無い判断のため）
- リサーチ・要約・大量処理: 軽量モデル
- LLM 採点（eval-loop 等）の閾値は、使うモデルの採点傾向を見て調整する
```

## 3. 設定場所は4つ（実測・公式照合済み）

| 場所 | 書き方 | 効く範囲 |
|---|---|---|
| **agent 定義**（`.claude/agents/<name>.md`） | frontmatter に `model: sonnet` など（`inherit` で親と同じ） | その agent が起動するたび |
| **skill frontmatter** | `model:` / `effort:` | そのターンのみ。`context: fork` 付きなら**フォーク先サブエージェントのモデル**になる |
| **CLAUDE.md の方針節** | 上記雛形（宣言的） | Agent ツールでサブエージェントを起動するときの選択指針 |
| **`/model`** | セッション中に手で切替（`--global` で既定化） | セッション全体 |

実例（この環境で動いているもの）:
- TDD の `tester` / `implementer` / `coder` → `model: sonnet`
  （テストが検証器なので実装側は中位で足りる、の実装）
- `delegate-llm-debate` → `model: opus`（統合判断なので上位）

## 4. ループ・評価との組み合わせ

- **eval-loop**: 生成側は軽く、評価側（evaluator）は強く、が基本。
  評価は検証器の無い判断そのものだから
- **LLM 採点の閾値はモデル依存**。モデルごとに採点の癖（甘い/辛い/分散）が違うため、
  モデルを変えたら閾値を据え置かない。数回走らせて傾向を見てから決める
- 軽いモデルで採点させる場合は、採点軸を**狭く・具体的に**する
  （抽象的な観点を「察して」一貫採点できるのは上位モデルだけ）

## 5. 生成時のルール

- **推測でモデル名を書かない。** 生成時点で利用可能なモデル（`/model` の選択肢）を確認する
- グローバル CLAUDE.md に方針が既にあれば、プロジェクト側は**差分だけ**
  （差分が無いなら節ごと省略してよい — 書かないことも設計）
- カスタム agent を生成するときは `model:` を必ず明示する
  （未指定はセッションモデル継承 = 意図しない高コストや能力不足の温床）
- コスト注意も1行添える: 上位モデルの並列起動・長いループは課金が跳ねる
