# ハーネスのライフサイクル — 立ち上げた後にどう育てるか

本キットが生成するのは**骨格（スナップショット）**でしかない。
ハーネスの価値の大半は、運用の中で育つ側にある。
Phase 5 の引き渡しでこの文書の要点を伝え、生成する CLAUDE.md に「育て方」の節を入れる。

各要素（hook・rules・スキル・連携）は別々の部品ではなく、
**この一つのサイクルの中の持ち場**である。

---

## 1. 失敗の昇格ラダー — 育ての基本動作

```
Level 0: チャットで指摘した        （セッションを跨がず消える）
Level 1: CLAUDE.md / Gotchas に書いた（読まれるが、確率的に無視される）
Level 2: 検証スクリプトにした       （exit code で確定。ただし実行が任意）
Level 3: hook / CI / deny にした    （通過必須。忘れても守られる）
```

**同じ失敗が2回起きたら、1つ上の Level へ。** 判断は3つを総合する:

- **再発頻度** — 月に何度もハマるなら、その Level はもう負けている
- **爆発半径** — 本番事故・データ破壊級なら、低頻度でも一気に上へ
- **決定論で書けるか** — 機械で判定できるものは Gotchas に置かず**最初から Level 2〜3 へ**。
  注意力で確率的に防ぐより、ルールで100%防ぐほうが常に安い

記憶の最終形態は「**覚えていなくても守られる構造**」。
Gotchas は昇格までの一時置き場であって、ゴールではない。

---

## 2. 記憶の格上げ — どの層に置くかは頻度が決める

置き場所は静的に決めるものではなく、**呼ばれる頻度を見て動かす**。

```
docs（書き溜め・帯域ゼロ）
  → 頻繁に参照されるようになったら → 参照スキル（description で想起される圧縮記憶）
    → 毎セッション要ることが確認できたら → CLAUDE.md（常駐・最も高価な層）
```

- **まず一番安い層（docs）に書く。** 価値が確認できたものだけを高い層へ運ぶ
- 逆向きも同じ基準で行う: 呼ばれなくなった常駐記述は**降格・削除**する
- **stale な記述は無いより悪い。** 古い前提はエージェントを存在しない問題に追わせる。
  削るコストはほぼゼロ、残すコストはトークンと誤誘導

---

## 3. 検証の階段 — 何をどの段で守るか

```
① 機械の○×      hook / CI / lint / test — 確定的に判定できるものすべて
② 内ループ       eval-loop 等: evaluation.md を基準に閾値まで自動で詰める
③ 出荷前の1周    採点基準を知らない読み手による検査（goal-loop 系）。説得系のみ・毎回は不要
④ 人間の凝縮点   どれがいいか → bestofn ／ これでいいか → akapen。
                 自己検証できるものには人間を挟まない
⑤ 定期診断       audit-harness 等でハーネス全体を見直す
```

**原則: 下の段で守れるものを、上の段に持ち込まない。**
①で弾けるものを②の LLM 採点に渡すのはトークンの無駄で、
②で詰められるものに④の人間を毎回付き合わせるのは承認疲れを生む。
人間の判断は減るのではなく、④の少数のポイントに**凝縮**される。

Phase 2 のインタビュー「完了をどう判定するか」の答えは、この階段に対応させる:
テストで判定できる → ①だけで足りる ／ 客観テストが無い → ②を軸に ／
好み・視覚が絡む → ④を要所に置く。

---

## 4. 棚卸し — 増えたものを減らす

スキル・ルール・連携は放置すると増える一方で、
**使われていないスキルの description も全セッションで帯域を消費し続ける**。

**棚卸しのトリガーを意図的に設ける**（自然に起きるのを待たない）:

- 人にハーネスを説明・共有・資料化するとき（重要でないものに自然に気づく）
- Claude Code 本体に大きな機能が追加されたとき（自作部分が公式機能で不要になっていないか）
- 四半期に一度

方法は2系統を併用する:

- **定量**: hook でスキル呼び出しを記録し、使用回数を集計する
- **定性**: LLM に「このハーネスの中でこのスキルは要るか」を判定させる

---

## 5. スキルの一生

```
同じ手順を3回繰り返した
  → /design-skill で「作るべきか・境界・発動条件」を設計
    → 作ったら実セッションで受け入れ確認
      （完了 = 成果物が出た AND 動作が止まった。自己申告ではなく実物で）
      → 運用で Gotchas を育てる
        → 再発する失敗は §1 のラダーで昇格
          → 呼ばれなくなったら §4 の棚卸しで削除
```

---

## 生成する CLAUDE.md に入れる「育て方」の節（この4行だけ）

```markdown
## ハーネスの育て方

- 同じ失敗が2回起きたら、注意書きではなく hook / deny / lint へ昇格させる
- 同じ手順を3回繰り返したら `/design-skill` でスキル化を検討する
- 人に説明するとき・本体の大型更新後が棚卸しの合図（使っていないものを削る）
- 構成を変えたくなったら `/setup-project` を再実行（補強モードで差分提案）
```

詳細をコピーしない。生成先のプロジェクトにこの文書は無いので、
**自己完結する4行**に圧縮して渡すのがこの節の役割。
