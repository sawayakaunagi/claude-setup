# 連携の導入判断 — MCP / プラグイン / foyer door

Phase 4 で扱う。**検出して示すだけ。押し付けない。**
入れれば入れるほど良くなるものではなく、どれも常時コンテキストを消費する（→C-1 帯域はゼロサム）。

```bash
# インストール済みプラグインと有効状態
cat ~/.claude/settings.json 2>/dev/null | sed -n '/enabledPlugins/,/}/p'
ls ~/.claude/plugins/marketplaces 2>/dev/null

# ユーザースコープのスキル・エージェント

# MCP 設定

# foyer
```

## 1. MCP — CLI で代替できないか先に確認する

MCP サーバはツール定義が**常時コンテキストに載る**。GitHub MCP で 23k〜50k トークン、
同じことを `gh` CLI でやればゼロ。帯域はゼロサムなので、その分だけタスク本体が押し出される（→C-1）。

### 判断フロー

```
そのサービスに CLI はあるか？
  ├ ある  → CLI を使う。CLAUDE.md にコマンド例を2〜3行書く
  └ ない  → MCP を検討
              └ 使うツールは限られるか？
                    ├ 限られる → 導入。使わないツールは無効化を検討
                    └ 全面的に使う → 導入
```

| やりたいこと | CLI で足りる | MCP が要る |
|---|---|---|
| GitHub 操作 | `gh` | — |
| Vercel 操作 | `vercel` | — |
| DB 参照 | `psql` / `sqlite3` | — |
| ブラウザ操作 | — | claude-in-chrome 等 |
| SaaS の独自 API | curl で書けるなら CLI | 認証が複雑なら MCP |

**既に入っている MCP を消せとは言わない。** 新規に足すときだけこの判断を通す。

## 2. プラグイン — このプロジェクトで実際に回るものだけ

有効化は `~/.claude/settings.json` の `enabledPlugins`（ユーザースコープ）で管理されている。
つまり**プロジェクト単位の切り替えではなく、全プロジェクトに効く**。
「このプロジェクトのために有効化する」は、他の全プロジェクトにも description が載ることを意味する。

だから提示はこの形にする:

```
このプロジェクトで効きそうなプラグイン:
  eval-loop  — evaluation.md を採点基準にした品質ループが回せます（未有効）
  
有効化はユーザースコープ（全プロジェクトに効く）です。有効にしますか？
```

### 種別ごとの候補

| 種別 | 候補 | 効く理由 |
|---|---|---|
| コード開発型 | TDD 系スキル、`akapen` | 決定論的検証を回す／作る前の確認 |
| 文書・ワークフロー型 | `eval-loop`、`bestofn`、`akapen` | 客観テストが無い部分をループと人間の選択で埋める |
| 両方 | `skill-creator` | 後からスキルを作るとき |

### 未インストールのものは入手先を示すだけ

インストールを代行しない。**プラグインは `claude plugin install` が成功しても、
再起動するまでそのセッションでは呼べない**（`Unknown skill` になる）。
その場でインストールすると「入ったのに使えない」状態でユーザーを混乱させる。

```
eval-loop は未インストールです。使う場合:
  /plugin marketplace add <配布元>
  /plugin install eval-loop
  → Claude Code を再起動
```

## 3. foyer door — 他プロジェクトへの窓口

`foyer` があるなら、立ち上げたプロジェクトを door として登録しておくと、
**他のディレクトリからこのプロジェクトに質問できる**ようになる。

母艦から grep して回るのではなく door 越しに聞く形になるので、
違うディレクトリを掴ませる事故が減る。

### 登録の判断

| 登録する | 登録しない |
|---|---|
| 他プロジェクトから参照されうる知識がある | 使い捨て・実験用 |
| 継続的に育てるプロジェクト | 単発の作業ディレクトリ |

### desc の書き方

door の `desc` は**カタログに出る一行**。ここが曖昧だと、後から探すときに選べない。
「何のプロジェクトか」だけでなく **「何に詳しいか」** を書く。

```
✗ 「記事作成プロジェクト」
✓ 「note 記事の執筆ハーネス。取材メモから構成・執筆・校正まで。文体規約と
    禁止語リスト、evaluation.md による採点基準に詳しい」
```

登録は `foyer` の作法に従う（詳細は `ref-foyer` スキルがあればそちらを参照）。
**登録コマンドを代行する前にユーザーの承認を取る**（設定が他ディレクトリから見える状態になるため）。

## 4. 何も足さないという結論も正しい

Phase 4 の既定は**「候補を示して、要らなければ何も足さない」**。

立ち上げ直後は何が必要か分からない。使わない連携を先に入れると、
description が全セッションのコンテキストを食い続ける（→C-1）。
必要になった時点で足すほうが、常に安い。

生成する CLAUDE.md に1行だけ残しておく:

```markdown
## 連携
現時点では追加なし。必要になったら `/setup-project` を再実行すると候補を再提示する。
```
