# 連携の導入判断 — MCP / プラグイン / CLI ツール / foyer door

Phase 4 で扱う。**検出して示すだけ。押し付けない。**
入れれば入れるほど良くなるものではなく、どれも常時コンテキストを消費する（→C-1 帯域はゼロサム）。

ただし「示すだけ」で終わらせない。**導入済みのツールを検出したら、
そのプロジェクトに合わせた配線（CLAUDE.md への1行・初期化コマンド・最初のルール）まで提案する。**
入っているのに配線されていないツールは、無いのと同じ。

---

## 検出コマンド

```bash
# インストール済みプラグインと有効状態
claude plugin list 2>/dev/null | head -40

# 連携カタログ対象の CLI（あるものだけ配線を提案する）
for c in bon bd foyer toolhint gh; do command -v "$c" >/dev/null 2>&1 && echo "$c ✓"; done

# ユーザースコープのスキル・エージェント
ls ~/.claude/skills ~/.claude/agents 2>/dev/null

# MCP 設定
ls .mcp.json .claude/mcp.json 2>/dev/null
```

## 1. MCP — CLI で代替できないか先に確認する

MCP サーバはツール定義が**常時コンテキストに載る**。GitHub MCP で 23k〜50k トークン、
同じことを `gh` CLI でやればゼロ。帯域はゼロサムなので、その分だけタスク本体が押し出される（→C-1）。

### 判断フロー

```
そのサービスに CLI はあるか？
  ├ ある  → CLI を使う。CLAUDE.md にコマンド例を2〜3行書く
  └ ない  → MCP を検討
              └ 使うツールは限られるか？
                    ├ 限られる → 導入。使わないツールは無効化を検討
                    └ 全面的に使う → 導入
```

| やりたいこと | CLI で足りる | MCP が要る |
|---|---|---|
| GitHub 操作 | `gh` | — |
| Vercel 操作 | `vercel` | — |
| DB 参照 | `psql` / `sqlite3` | — |
| ブラウザ操作 | — | claude-in-chrome 等 |
| SaaS の独自 API | curl で書けるなら CLI | 認証が複雑なら MCP |

**既に入っている MCP を消せとは言わない。** 新規に足すときだけこの判断を通す。

## 2. プラグイン — スコープを選ばせる

インストールには**スコープが3つ**ある（`claude plugin install --scope <scope>`）。
既定は `user` なので、何も指定しないと**全プロジェクトに効き、
他の全プロジェクトにも description が載る**。

| スコープ | 効く範囲 | 適する場面 |
|---|---|---|
| `user`（既定） | 全プロジェクト | どこでも使う汎用プラグイン |
| `project` | そのプロジェクトだけ。コラボレーターにも共有される | プロジェクト専用の連携 |
| `local` | そのプロジェクトの自分だけ | 個人的に試す段階 |

**このスキルの文脈（プロジェクトごとにハーネスを敷く）では、
`--scope project` が既定候補**。全プロジェクトで使うと分かっているものだけ `user` にする。

**注意: `claude plugin marketplace add` は第三者コードの実行になりうる。**
スキルの `!` 構文や hook は導入後に実行される。中身を読んでから入れる、
とユーザーに一言添える（自分が作ったものでも、この習慣ごと渡す）。

**インストールを代行しない。** プラグインは install が成功しても、
再起動するまでそのセッションでは呼べない（`Unknown skill` になる）。
その場でインストールすると「入ったのに使えない」状態でユーザーを混乱させる。

## 3. 連携カタログ — 検出したら配線まで提案する

> **入手性の注意:** ここに挙げるツールのうち `beads` 以外は、2026-08 時点で
> **公開リポジトリではない**（配布元のメンバーシップ経由で配られている）。
> 未導入の場合は「こういうツールがある」と名前を伝えるに留め、
> 入手先の URL を案内しない（リンク切れを案内することになる）。
> **導入済みを検出した場合のみ**、以下の配線を提案する。

### 品質収束ループ — `eval-loop`

**何をするか:** 作る係と採点する係を分け、スコアが合格ラインに達するまで
「生成 → 採点 → 修正」を自動で回す。判定は Stop hook のシェル整数比較（AI の気分に依存しない）。

**効く場面:** 文書型プロジェクト全般。テストが無い成果物の品質を一定ラインまで自動で上げる。

**配線（導入済みなら提案する）:**
1. 本キットが生成した `evaluation.md` の品質軸を、そのまま起動時の採点基準に流用できる。
   CLAUDE.md に起動例を1行書く:
   ```
   品質ループ: /run-eval-loop <タスク> criteria: <evaluation.md の品質軸> threshold: 90
   ```
2. `evaluation.md` は deny で保護済みのはず（→recipe-docs §1）。
   これが評価器から「基準を緩めて合格する」裏口を塞ぐ

**規律（CLAUDE.md に書き添える価値があるもの）:**
- **1周 = 生成と採点で AI 2回課金。** max を大きくするほど料金は積み上がる
- 3周続けて同点なら堂々巡り — 打ち切る
- max 到達で不合格なら、ループより先に**目標（合格点・採点軸）を疑う**
- LLM 採点には ±10 点程度のノイズ。閾値は 90 前後が現実的で、100 点を求めると収束しない

**`run-goal-loop` が同梱されている版なら:** ふだんの磨き込みは通常ループ、
**出荷前に1周だけ** goal-loop（採点基準を知らない読み手による検査）。
説得系（LP・コピー・文章）で効き、テストで正解が出る機能系には過剰。

### 複数案から人が選ぶ — `bestofn`（`bon` CLI）

**何をするか:** N 案を並列生成し、ブラウザの arena で人間が1案選ぶ。
採用案と理由が機械可読でエージェントに戻る。

**効く場面:** 正解が1つに決まらない分岐（見出し・構成・トーン・デザインの方向）。
検証器が書けない問題では、人間が検証器になる。

**配線:** 分岐が好みで決まる工程を持つプロジェクトなら、CLAUDE.md に1行:
```
方向性が割れる成果物（見出し・構成案など）は bestofn で N 案を出して選ぶ
```

**規律・落とし穴:**
- **N 案の生成はほぼ N 倍のトークン。**「N 案出せば必ず良くなる」は誤り
- エージェントから `bon serve` を前面で呼ぶとブロックして止まる — **必ず `bon serve -d`**
- `bon wait` の `WAITING:` 出力は失敗ではなく安全脱出。再実行して待ち直せる

### 作る前に1案を確認 — `akapen`

**何をするか:** 実装前に、UI 案・設計案を赤ペン注記つきの HTML 1枚にして人に見せ、
フォームの回答を反映してから作る。サーバ不要・`file://` で完結。

**効く場面:** テキストでは伝わらない**視覚差分**の確認
（ボタン配置・レイアウト等）。テキスト2択で足りる分岐なら AskUserQuestion でよい。

**配線:** UI を持つプロジェクトなら CLAUDE.md に1行:
```
UI の配置・見た目に関わる変更は、実装前に「赤ペンして」で確認を取る
```

### 使い分けは1行で覚えられる

```
どれがいいか → bestofn ／ これでいいか → akapen ／ 正解が一意で自己検証できる → 開催しない
```

3つ目が一番大事。**自己検証できるもの（テスト・lint で判定できるもの）に
人間の判断を挟むのはコストの無駄**で、承認疲れを生む。

### 操作の瞬間に思い出させる — `toolhint`

**何をするか:** エージェントがコマンドを打つ直前（操作きっかけ）や、
特定の語を含む発言（ことばきっかけ）に反応して、docs の**置き場所を指す1行だけ**を注入する。
読むかどうかはエージェントが決める。hook は fail-open（壊れても作業は止まらない）。

**効く場面:** 「書いてあるのに読まれない」自作 CLI の使い方・チーム内の造語。
**いつ読んでも効く規約は CLAUDE.md へ、その操作の瞬間だけ思い出せばいいものは toolhint へ**、が線引き。

**配線:** プロジェクト固有の CLI や規約があるなら、project 層
（`<dir>/.claude/toolhint/`）に最初のルールを1本置くことを提案する。
ルールの実体は3行（`tool:` / `match:` / `doc:`）＋ docs 1枚。
`toolhint test "<入力>"` で state を変えずに発火を確認できる。

### 長期タスクと依存関係 — `beads`（`bd` CLI・public OSS）

**何をするか:** AI エージェント向けの依存グラフ型イシュートラッカー兼構造化メモリ。
`bd ready` で着手可能タスクを判定し、`--claim` で並行作業の競合を防ぐ。
唯一 public（`gastownhall/beads`。brew / npm で導入可）。

**効く場面:** 依存関係・ブロッカーが多い長期プロジェクト、ロングランのタスク。
Claude Code 組み込みの TODO ツールでは前後関係が構造として残らない場合の置き換え。

**配線（導入済み・または導入希望なら）:**
```bash
bd init            # リポジトリに初期化
bd setup claude    # Claude Code 統合（hooks + prime 注入）
```
イシューの**受け入れ条件**欄に完了基準を書く運用にすると、
生成側と評価側の合意点として機能する（`evaluation.md` と同じ思想のタスク粒度版）。

**規律:**
- `bd remember` は使わない（prime のコンテキストが肥大化して汚す）。記憶は外部で設計する
- タスクをクローズするとき、次の担当（人間/エージェント）が読めるノートを残す
- 人間の承認を待たせたい箇所は gate イシューで止める

### 他プロジェクトへの窓口 — `foyer`

**何をするか:** プロジェクトディレクトリを「door」として登録し、
他のディレクトリから `foyer ask <door> "質問"` で聞ける。
door の向こうでは**そのプロジェクトの CLAUDE.md・skills・permissions がフルで効いた状態**で動く。

**効く場面:** このプロジェクトの知見を他プロジェクトから参照させたいとき。
plugin として取り込むとコンテキストが汚れるが、door なら**カタログを引く数行だけ**で済む。

**配線:** 継続的に育てるプロジェクトなら door 登録を提案する。
`desc` は人間向けのラベルではなく**読むエージェント向け**に「何に詳しいか」を書く:

```
✗ 「記事作成プロジェクト」
✓ 「note 記事の執筆ハーネス。取材メモから構成・執筆・校正まで。
    文体規約と evaluation.md による採点基準に詳しい」
```

**登録コマンドを代行する前にユーザーの承認を取る**
（設定が他ディレクトリから見える状態になるため）。使い捨てのプロジェクトは登録しない。

## 4. 何も足さないという結論も正しい

Phase 4 の既定は**「候補を示して、要らなければ何も足さない」**。

立ち上げ直後は何が必要か分からない。使わない連携を先に入れると、
description が全セッションのコンテキストを食い続ける（→C-1）。
必要になった時点で足すほうが、常に安い。

生成する CLAUDE.md に1行だけ残しておく:

```markdown
## 連携
現時点では追加なし。必要になったら `/setup-project` を再実行すると候補を再提示する。
```
