# CLAUDE.md / rules / ドキュメント構成

CLAUDE.md に全部書くと肥大化する。**「いつ載るか」で置き場所を分ける**のがこの文書の主題。

> 検証環境: Claude Code v2.1.220（2026-08 実測）。挙動はバージョンで変わるので、
> 生成後は Phase 5 の `/context` で実際にロードされたかを確認する。

---

## 1. 「いつ載るか」で置き場所を決める

| 置き場所 | 載るタイミング | コンテキスト費用 |
|---|---|---|
| `CLAUDE.md` | **毎セッション必ず** | 常時。全プロジェクトの全作業で払う |
| `.claude/rules/*.md`（`paths:` 無し） | **毎セッション必ず** | 常時。CLAUDE.md と同じ |
| `.claude/rules/*.md`（`paths:` 有り） | **該当ファイルを読んだとき** | 触ったときだけ |
| `.claude/skills/*/SKILL.md` | description は常時、本文は**発動時** | description のみ常時 |
| `.docs/**`（素の Markdown） | **エージェントが辿ったときだけ** | ゼロ |

**判断:** 全作業で例外なく要るものだけを CLAUDE.md に置く。
「Python を触るときだけ」「API を書くときだけ」は `paths:` 付き rules へ落とす。

### もう1つの軸 — 「届く」か「引きに行くか」

置き場所を選ぶとき、「いつ載るか」と直交するもう1つの軸がある。

| 向き | 器 | 性質 |
|---|---|---|
| **届く**（push） | CLAUDE.md / rules / hook で注入するポインタ | エージェントが求めていなくても入る。**確実だが、詰め込むほど効かなくなる** |
| **引きに行く**（pull） | `.docs/**` / 素の Markdown リンク / スキルの補助ファイル | エージェントが必要と判断したときだけ読む。**帯域ゼロだが、辿られなければ存在しないのと同じ** |

docs が効くかどうかは「どこに書いたか」ではなく「**いつ届いたか**」で決まる。
「この操作の瞬間に思い出してほしい」と言えるものだけを push 側（hook でポインタ1行を注入）へ回し、
いつ読んでも役に立つ参照は pull 側に置いて CLAUDE.md からポインタで指す。
push 側の器は詰め込みたくなるが、増えるほど何がいつ効いたのか追えなくなる——
入れるのは本当に要るものだけにする。

## 2. `.claude/rules/` — パススコープ規約

### 書式

```markdown
---
paths:
  - "src/api/**/*.ts"
  - "tests/**/*.test.ts"
---

# API 開発ルール

- 全エンドポイントで入力バリデーションを行う
- エラーレスポンスは標準形式を使う
```

- `.claude/rules/**/*.md` が再帰的に発見される。サブディレクトリで整理してよい
- `paths:` を**書かなければ常時ロード**（`.claude/CLAUDE.md` と同じ優先度）
- ユーザーレベルは `~/.claude/rules/`。プロジェクト rules のほうが優先される
- ブレース展開可: `"src/**/*.{ts,tsx}"`

### 実測で確認したこと（v2.1.220）

- `paths:` は**正しくスコープされる**。該当ファイルを読むと載り、読まなければ載らない
- 「`paths:` が効かず `globs:` を使え」という報告が出回っているが、**v2.1.220 では `paths:` で動く**。
  公式ドキュメントの記載も `paths:`。**`paths:` を使う**

### 落とし穴

| 落とし穴 | 意味 |
|---|---|
| **Read で発火する。Write では発火しない** | 新規ファイルを作るだけのときは載らない。「新しく作る Python はこう書く」を rules だけに頼らない |
| **compaction 後に再注入されない** | project-root の CLAUDE.md は再注入されるが、path-scoped rules は次に該当ファイルを読むまで復帰しない |
| 常に守らせたい制約を `paths:` に入れる | 上2つの理由で穴が空く。**絶対に守らせたい制約は CLAUDE.md か hook へ** |

**使い分けの結論:** rules は「あると品質が上がる規約」向き。
「破られたら困る制約」は CLAUDE.md（説明）＋ hook / deny（強制）で二重に持つ。

## 3. 段階的開示 — リンクと import は別物

ここは取り違えが多い。**目的が逆になる。**

| 書き方 | 挙動 | コンテキスト |
|---|---|---|
| `[.docs/decisions/](./docs/decisions/)`（素のリンク） | エージェントが**必要と判断したとき辿る** | **ゼロ**。辿ったぶんだけ |
| `@docs/git-instructions.md`（import） | **launch 時に展開されて載る** | 中身のぶん常時かかる |

**コンテキストを減らしたいなら素の Markdown リンク。** `@` import は
「複数ファイルに分けて整理したいが、内容は毎回必要」というときに使うもので、
**節約にはならない**（公式ドキュメントも明記）。

CLAUDE.md には**ポインタだけ**書く:

```markdown
## 設計判断の経緯
`.docs/decisions/` を参照（ADR 形式）

## API の詳細仕様
`.docs/references/api.md` を参照
```

## 4. ドキュメントツリー

エージェンティック検索が強いので、**ディレクトリ名から中身を推測させる**のが効く。

```
project/
├── CLAUDE.md              # 軽量に保つ。ポインタ中心
├── .claude/
│   ├── rules/             # ファイル種別ごとの規約（paths: 付き）
│   ├── skills/            # 繰り返す手順
│   ├── hooks/             # 自動矯正
│   └── settings.json      # 権限
└── .docs/
    ├── decisions/         # なぜそうしたか（ADR）
    ├── guides/            # どうやるか
    └── references/        # 詳細仕様
```

**初回に全部作らない。** 空ディレクトリを並べても中身が無ければ意味がない。
`CLAUDE.md` と `.claude/settings.json` から始め、必要になった階層だけ足す。

`decisions/` は特に効く。「なぜこの構成なのか」が残っていないと、
次のセッションが良かれと思って作り直す（→D-1 暗黙の前提）。

## 5. CLAUDE.md の書き方（公式推奨と整合）

- **200行以下を目安にする。** 超えると追従率が落ちる（公式ガイダンス）。
  本キットは 50行程度で立ち上げ、運用しながら育てる前提
- **HTML コメントはコンテキストを消費しない。** 注入前に除去されるので、
  人間向けの注記を無料で書ける

  ```markdown
  <!-- この deny は 2026-08 のインシデント後に追加。外すなら要相談 -->
  ```

- **矛盾する記述を残さない。** 2つのルールが衝突すると、どちらが選ばれるか不定になる

## 6. `AGENTS.md` がある場合

**Claude Code は `AGENTS.md` を読まない。** 他のエージェント向けに用意されていても素通りする。

既に `AGENTS.md` があるプロジェクトでは、`CLAUDE.md` の先頭に import を置くことを提案する
（二重管理を避けられる）。

```markdown
@AGENTS.md

## Claude Code 固有
（ここに Claude Code だけの指示を足す）
```

symlink でも良いが、Claude 固有の追記ができなくなる。Windows では管理者権限が要るので
import のほうが無難。

**勝手に書き換えない。** 既存の `AGENTS.md` は他ツールが読んでいる可能性がある。
提案して承認を取る。

## 7. `/init` との関係

Claude Code には公式の `/init` があり、CLAUDE.md を自動生成する
（`CLAUDE_CODE_NEW_INIT=1` で CLAUDE.md・skills・hooks を対話的に作る multi-phase フローになる）。

**競合しない。役割が違う。**

| | `/init` | 本キット |
|---|---|---|
| 主眼 | コードベースを読んで CLAUDE.md を書く | **権限と検証の設計**（deny / hook / 評価基準の保護） |
| 対象 | コードベース前提 | コード型 **/ 文書ワークフロー型**を判定して分岐 |
| 設計の根拠 | — | agent-essence の原則ID。`audit-harness` で答え合わせできる |

**既に `/init` を実行済みのプロジェクトでは、その CLAUDE.md を尊重する。**
補強モードで扱い、上書きせず不足分（permissions・hooks・rules）だけを足す。

逆に「CLAUDE.md をちゃんと書きたい」が主目的なら、`/init` を先に走らせてから
本キットで補強するほうが早い。Phase 1 でそう案内してよい。
