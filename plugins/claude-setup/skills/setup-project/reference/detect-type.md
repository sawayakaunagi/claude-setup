# 種別判定 — コード開発型 / 文書・ワークフロー型

## なぜ判定するのか

両者は**「完了を誰が保証するか」が構造的に違う**（→C-4 自己申告は完了の証拠にならない）。

| | コード開発型 | 文書・ワークフロー型 |
|---|---|---|
| 完了の判定 | テスト・型チェック・CI が**決定論的に**出す | 客観的な合否が存在しない |
| 主たる矯正手段 | 決定論的ツール（→V-1） | LLM 採点 + 人間の選択（→E-3） |
| 守るべき評価基準 | テストコード・lint 設定 | 評価軸を書いた文書そのもの |
| 典型の失敗 | テストを書き換えて緑にする（→C-5） | 評価軸を都合よく読み替える（→C-5） |

同じ deny リストとハーネスを両方に当てても効かない。だから最初に分ける。

---

## 判定シグナル

### 収集コマンド

```bash
# ビルドマニフェスト
ls package.json pyproject.toml go.mod Cargo.toml Gemfile pom.xml build.gradle \
   composer.json *.csproj Makefile 2>/dev/null

# テストの器
ls -d test tests __tests__ spec e2e 2>/dev/null

# ファイル構成の傾向（上位10拡張子）
find . -type f -not -path './.git/*' -not -path './node_modules/*' \
  | sed -nE 's/.*\.([A-Za-z0-9]+)$/\1/p' | sort | uniq -c | sort -rn | head -10

# 既存ハーネスの有無（成熟度判定にも使う）
ls CLAUDE.md AGENTS.md .claude/settings.json 2>/dev/null
ls -d .claude/skills .claude/agents 2>/dev/null
```

### 判定表

| 種別 | シグナル |
|---|---|
| **コード開発型** | ビルドマニフェストが1つ以上ある。または `.ts/.py/.go/.rs/.java` 等が拡張子上位を占める |
| **文書・ワークフロー型** | ビルドマニフェストが無い。かつ `.md/.txt/.csv/.xlsx/.docx/.json(データ)` が上位 |
| **混合** | 両方のシグナルが強い（例: 記事を書くリポジトリに生成スクリプトがある） |
| **空** | 追跡対象ファイルがほぼ無い |

## 判定は自動、確定はユーザー

**検出結果を提示して確認を取る。自動で確定しない。**

誤判定のコストが非対称だから。コード型を文書型と誤ると、テスト保護の deny が入らないまま
実装が始まる（→C-5 が野放しになる）。逆に文書型をコード型と誤ると、存在しないテストコマンドが
CLAUDE.md に書かれ、以後のセッションが嘘の前提で動く（→D-2 嘘を教える）。

提示の形:

```
検出結果:
  package.json あり / tests/ あり / .ts が 142 ファイル
  → コード開発型 と判定しました

この判定で進めてよいですか？（違う場合は種別を教えてください）
```

---

## 混合のとき

**主たる成果物がどちらかで決める。副次側は「補助」として扱う。**

例: 記事リポジトリに生成スクリプトがある
→ 文書・ワークフロー型として立てる。スクリプトは補助なので、
   テスト保護の deny は入れず、`evaluation.md` を主軸にする。

例: Web アプリのリポジトリに README とドキュメントが大量にある
→ コード開発型。文書は成果物ではないので、文書型のレシピは適用しない。

判断に迷ったら**ユーザーに「このリポジトリで一番大事な成果物は何ですか」と聞く**。
「テストが通れば完成か、人が読んで良ければ完成か」で切り分けられる。

両方が本当に主軸なら、コード開発型で立てたうえで、
文書側のディレクトリにだけ `evaluation.md` を置く（部分適用）。

---

## 空ディレクトリのとき

判定材料が無いので聞く。ここでスタックまで決まると以降が全部具体化するので、
**この1問だけは丁寧に聞く価値がある**。

聞くこと:
1. 何を作るか（成果物の形）
2. 使う技術（決まっていれば）

決まっていなければ、**種別だけ決めて最小構成で立てる**。
スタックが確定した時点で `setup-project` を再実行すれば補強モードで差分が入る。
「まだ決まっていないので後で」を選べるようにしておく（憶測でスタックを書くと →D-2 になる）。

---

## 成熟度判定（種別と直交）

種別とは別に、**既にハーネスがあるか**で動作モードが変わる。

| 条件 | モード |
|---|---|
| `CLAUDE.md` も `.claude/settings.json` も無い | **ブートストラップ** — 一式を生成 |
| どちらかがある | **補強** — 差分だけ提案 |

補強モードでは**既存ファイルを上書きしない**。既存の CLAUDE.md には人間が書いた
意図が入っている可能性が高く、失うと戻せない。追記案を提示して承認を取る。
