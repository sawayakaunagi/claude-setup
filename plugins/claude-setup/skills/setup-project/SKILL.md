# setup-project

このプロジェクトに合ったハーネスを生成する。`audit-harness` が「作った後に何が間違っているか」を
診断するのに対し、本スキルは**最初から正しく敷く**側を担う。同じ原則語彙（`agent-essence` の
C / T / K / V / S / E）を共有しているので、生成後にそのまま診断で答え合わせできる。

- **Input**: `$ARGUMENTS` = 対象ディレクトリ（省略時はカレント）
- **Output**: 対象ディレクトリに `CLAUDE.md` / `.claude/settings.json` / `.claude/hooks/*` 等を生成。
  何を入れて何を入れなかったかを標準出力で報告する

## 同梱リファレンス（段階的に読む）

全部を最初に読まない（→C-1 帯域はゼロサム）。**必要になった時点で1本ずつ読む。**

| ファイル | いつ読むか |
|---|---|
| `reference/detect-type.md` | Phase 1 の最初 |
| `reference/recipe-code.md` | Phase 3・コード開発型と確定したときだけ |
| `reference/recipe-docs.md` | Phase 3・文書型と確定したときだけ |
| `reference/settings-catalog.md` | Phase 3 で settings.json を組むとき |
| `reference/rules-and-docs.md` | Phase 3・CLAUDE.md の置き場所や `.claude/rules/` を考えるとき |
| `reference/integrations.md` | Phase 4 |
| `reference/harness-lifecycle.md` | Phase 5・引き渡しで「育て方」を渡すとき |

---

## Phase 1. 現状収集と判定

`reference/detect-type.md` を読み、そこにある収集コマンドを実行する。

### 1-1. 成熟度 → モード決定

| 条件 | モード |
|---|---|
| `CLAUDE.md` も `.claude/settings.json` も無い | **ブートストラップ** |
| どちらかがある | **補強** |

**補強モードでは既存ファイルを絶対に上書きしない。** 既存の CLAUDE.md には人間が書いた意図が
入っている可能性が高く、失うと戻せない。差分を提示して承認を取ってから追記する。

`/init` で生成された CLAUDE.md も同じく尊重する。本スキルの主眼は**権限と検証の設計**なので、
CLAUDE.md が既にあるなら、それを土台に permissions・hooks・rules を足すほうが速い。

**CLAUDE.md が無く、コードベースが大きい場合**は、先に `/init` を走らせてから
本スキルで補強することを提案してよい（コードベースの読み取りは `/init` のほうが得意）。
どちらでも成立するので、押し付けずに選ばせる。

### 1-2. `AGENTS.md` があったら

**Claude Code は `AGENTS.md` を読まない。** 置いてあっても素通りする。
既にあるなら、`CLAUDE.md` の先頭に `@AGENTS.md` の import を置く案を提示する
（詳細は `reference/rules-and-docs.md`）。**既存の `AGENTS.md` は書き換えない**
（他ツールが読んでいる可能性がある）。

### 1-3. 種別判定 → ユーザーに確認

検出結果と判定理由を並べて提示し、**確認を取ってから確定する**。自動確定しない。

```
検出結果:
  package.json あり / tests/ あり / .ts が 142 ファイル
  → コード開発型 と判定しました

この判定で進めてよいですか？
```

混合・空ディレクトリの扱いは `detect-type.md` に従う。

## Phase 2. インタビュー

**最大4問。** 聞かなくても検出で分かることは聞かない（→C-1）。

1. **成果物は何か** — 空ディレクトリのときのみ必須。検出で分かるなら飛ばす
2. **完了をどう判定するか** — テストか、人の目か、両方か
3. **触られたら困るものはあるか** — テスト・評価軸・素材・設定ファイル
4. **外部に出る操作はあるか** — デプロイ・公開・課金・送信

「分からない」「まだ決めていない」を選べるようにする。
**憶測で埋めない。** 未確定のまま書いた前提は、以後のセッションが信じ続ける嘘になる（→D-2）。

## Phase 3. 生成

種別に応じて `recipe-code.md` **または** `recipe-docs.md` を読む（両方読まない）。
併せて `settings-catalog.md` を読み、Phase 2 の回答に該当する部品だけを選ぶ。

### 生成する順序

**この順序を守る**（→V-1.3 deny は最終防衛線であって主たる制御ではない）。

1. **CLAUDE.md** — 正しい経路を示す
2. **hooks** — 自動的に矯正する
3. **settings.json の deny** — 最後に塞ぐ

deny だけ厚くて CLAUDE.md が空、という構成にしない。

### ファイルは Write で作る。Bash に頼らない

`mkdir -p` を Bash で叩かない。**Write ツールは親ディレクトリを自動で作る。**

Bash は permissions の対象なので、環境によっては `mkdir` の一発で止まる。
そこで止まると **CLAUDE.md だけ生成されて settings.json が無い**という
中途半端な状態で終わる（実測済みの失敗モード）。

同じ理由で、生成物の確認に `cat` / `sed` / `find` を使わない。Read と Glob を使う。
Bash が必要なのは Phase 1 の検出と Phase 5 の hook 発火確認だけ。

`chmod +x` が要らないよう、hook は最初から **`bash <script>` の形で登録する**。

### 置き場所は動かさない。書けなければ「提案」にする

**`.claude/` 配下への書き込みは拒否されることがある**（実測）。
permissions と hook はエージェントの権限そのものを変えるので、
Claude Code が自動承認しないのは**正しい挙動**。対話セッションでは確認を求められる。

書く前にそれを伝える:

> `.claude/settings.json` を作ります。エージェントの権限を変えるファイルなので
> 確認を求められます。中身はこれです。（内容を提示）

**拒否された場合、置き場所を変えて回避しない。**

| ✗ やってはいけない | ✓ 正しい |
|---|---|
| `scripts/format-changed.sh` に逃がす | `.claude/hooks/format-changed.sh` のまま |
| `claude-settings.proposed.json` をルートに撒く | `.claude/settings.proposed.json` に置く（同じ `.claude/` 配下） |

場所を変えると、**守るべき対象まで変わってしまう**。
実際、`scripts/` に逃がすと `Edit(scripts/format-changed.sh)` を deny に足す必要が生まれ、
本来不要な行が増える。

`.claude/` 配下にすら書けなかったときは、**ファイルを作らずに内容を出力し**、
適用コマンドを添えて終わる。中途半端なファイルを残さない。

```
.claude/settings.json への書き込みが通りませんでした。
以下を手動で保存してください: （内容）
```

### 共通で入れるもの

種別を問わず:

- `.gitignore` に Claude 関連の行が無ければ追記を提案
  （`.claude/settings.local.json`、生成物の一時ディレクトリ等）
- CLAUDE.md に **「完了の定義」セクション**（→C-4）。
  Phase 2「完了をどう判定するか」の答えを**検証の階段**（`harness-lifecycle.md` §3）に
  対応させる: テストで判定できる→機械の○×だけで足りる ／ 客観テストが無い→内ループを軸に ／
  好み・視覚が絡む→人間の凝縮点を要所に
- CLAUDE.md に **「ハーネスの育て方」の4行**（`harness-lifecycle.md` 末尾の定型。
  失敗2回で昇格・3回でスキル化・棚卸しの合図・再実行で補強）。
  「Skills: まだ無し」の1行はこの節に含まれるので別立てにしない

### `.claude/rules/` は初回に作らない

立ち上げ時の CLAUDE.md は 50行程度なので切り出す必要がない。空の `rules/` を作っても意味はない。
例外は「ファイル種別ごとに明確に分かれる規約」が Phase 2 で出た場合のみ。
判断基準と書式は `reference/rules-and-docs.md`。

作る場合に必ず伝えること: **rules は該当ファイルを Read したときに載る。Write では載らない。**
破られたら困る制約を rules だけに置かない。

### スキルは初回に作らない

立ち上げ時点では何が繰り返されるか分からない。使われないスキルの description は
全セッションのコンテキストを食う。**既定はゼロ個。**
インタビューで「毎回やる決まった手順がある」と明示されたときだけ1つ作る。

### 採用しなかった部品の理由を残す

カタログの部品を**入れなかった理由**を1行、settings.json のコメントか CLAUDE.md に残す。
残さないと次のセッションが勝手に足すか、必要な追加をためらう。

## Phase 4. 連携の導入判断

`reference/integrations.md` を読み、MCP・プラグイン・連携 CLI（`bon` / `bd` /
`foyer` / `toolhint` 等）を検出する。

**未導入のものは候補を示すだけ。既定は「何も足さない」。**
一方、**導入済みを検出したツールは、カタログ（integrations.md §3）の配線まで提案する**
—— CLAUDE.md に書く1行、初期化コマンド、使い分けの規律。
入っているのに配線されていないツールは、無いのと同じ。

インストール・有効化・初期化（`bd init` 等）を代行する前に必ず承認を取る。
プラグインはスコープ（user / project / local）を選ばせる。

---

## Phase 5. 動作確認と引き渡し

生成したものは、**書いただけでは効いていない**。ここを飛ばさない（→C-4 自己申告は完了の証拠にならない）。

### 5-1. CLAUDE.md / rules がロードされたか

**生成した CLAUDE.md は、そのセッションには載っていない。** セッション開始時に読み込まれるため、
今書いたものは次のセッションから効く。これを伝えないと「書いたのに無視される」と誤解される。

確認方法をユーザーに渡す（次のセッションで実行してもらう）:

```
/context     → Memory files の一覧に CLAUDE.md が出るか
```

`.claude/rules/` を作った場合は、**該当ファイルを1つ Read させてから** `/context` を見る
（`paths:` 付きは読むまで載らない）。

### 5-2. hook が効いているか

hook を生成した場合、**実際に1ファイル編集して発火を確認する**。
`hooks` 配列へのネストを間違えるとエラーにならず**静かに無視される**ので、
設定した気になったまま何も起きない状態が一番危ない。

hook も**再起動するまで有効にならない**ことがある。その場でスクリプト単体を叩いて
挙動だけ先に確かめておくと切り分けが楽になる:

```bash
printf '{"file_path":"<対象ファイル>"}' | bash .claude/hooks/<script>.sh; echo "exit=$?"
```

確認できないときは「未確認」と正直に伝える。動いたことにしない。

### 5-3. 報告

`reference/harness-lifecycle.md` を読み、以下を必ず伝える。

- **何を作ったか** — ファイル一覧
- **何を入れなかったか、なぜか** — deny を絞った理由など
- **プレースホルダが残っている箇所** — 文書型の `evaluation.md` は特に
- **次のセッションから効くこと** — CLAUDE.md も settings.json も、今すぐには反映されない
- **後から緩められること** — きつすぎたら言ってほしい、と明示する
- **これは骨格であり、育て方が本体であること** — 失敗の昇格ラダーと
  記憶の格上げ（lifecycle §1〜2）を1段落で要約して渡す。
  生成した各部品（hook・rules・スキル候補・連携）は別々の道具ではなく、
  このサイクルの中の持ち場である、という位置づけまで含める

### 5-4. 答え合わせ

`audit-harness` が使えるなら実行を提案する（生成側を診断側で採点する）。
無ければ「後からハーネス診断で確認できる」とだけ伝え、**入手を強要しない**。

## Gotchas

- **上書きしない。** 補強モードで既存 CLAUDE.md を書き換えるのは最悪の失敗。追記案の提示に留める
- **存在しないコマンド・パスを書かない。** `package.json` の `scripts` を実際に読む。
  推測で書いたコマンドは、以後のセッションが叩き続ける
- **deny に実在しないパスを並べない。** 無意味な行が残り、後から読む人を混乱させる
- **フォーマッタ hook は `|| true` で握る。** 未インストール環境で `exit 2` になると
  無関係な編集まで全部ブロックされて作業が止まる
- **hook スクリプトで `rg` を使わない。** hook は素の bash で走り、`rg` は環境によっては
  実体が無くシェル関数として提供されている。`command -v rg` でガードすると
  検査ごと黙ってスキップされる。関門となる検査は `grep` / `sed` だけで書く
- **文書型の hook は対象ディレクトリを絞る。** 全 `.md` に当てるとメモを書いた瞬間に止まる
- **プラグインのインストールを代行しない。** 再起動するまでそのセッションでは呼べないため、
  「入ったのに使えない」状態で混乱させる
- 生成物はあくまで骨格。**完璧な初期設定を目指さない**。運用しながら育てる前提で、
  最小で立ててから足すほうが常に安い
